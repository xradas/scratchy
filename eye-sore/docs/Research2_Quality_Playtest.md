Freeze one complete M0 profile before implementation comparisons; distinguish the lighting diagnostic shell from the playable mechanics room and C route. Technical identity/delivery checks must precede conclusions about player confusion, while fresh source listening can progress alongside mechanics work. The user's rejection of the sound remains a valid creative result; successful decoding, timing repair or more research cannot revoke it.

Reports describe candidates, not accepted canon. “GO” in a research tracker means proposed experiment scope, not user acceptance, implementation completion or measured quality.

## Evidence and research methods

**RF:** NN/g task guidance recommends realistic goals that avoid telling participants the solution; its think-aloud guidance distinguishes qualitative understanding from pure performance measurement. [Task scenarios](https://www.nngroup.com/articles/task-scenarios-usability-testing/), [think aloud](https://www.nngroup.com/articles/thinking-aloud-the-1-usability-tool/). **P:** ask “Reach the exit” or “What did you expect that enemy to do?” rather than “Follow the cobalt stripe” or “Did the heavier shotgun improve immersion?” Let first navigation be unprompted; use retrospective replay questions after demanding combat because continuous talk can alter pace/attention. User feedback is not a quiz about our lore.

**RF:** Microsoft's game accessibility guidance recommends additional channels for important cues, captions for meaningful audio and warns that simulated color-vision checks do not substitute for user testing. [XAG103](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/103), [XAG104](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/104). **P:** directly review mute/mono/caption and low-vision/contrast/control alternatives with the same state truth; recruit players with relevant needs when practical. A filter pass is a diagnostic, not a certification.

**RF:** Godot performance documentation distinguishes continuous frame cost, intermittent spikes and loading delay, recommends measurement across hardware, and discusses CPU/GPU profiling limitations. [Official optimization guidance](https://docs.godotengine.org/en/stable/tutorials/performance/general_optimization.html), [profiler](https://docs.godotengine.org/en/stable/tutorials/scripting/debug/the_profiler.html). **P:** measure named frame/callback/session workloads and compare capture-on/off; no blind optimization or average-FPS acceptance.

**RF:** id's released Doom state/action code establishes observable gameplay events rather than impressions alone; Auroch's developer account describes enemy state/animation/encounter authoring; Motive describes trial and iteration for coordinated intensity. [Doom state source](https://github.com/id-Software/DOOM/blob/master/linuxdoom-1.10/info.c), [Boltgun developer](https://blog.playstation.com/2023/04/11/warhammer-40-000-boltgun-releases-may-23-new-gameplay-details-revealed/), [Dead Space developer](https://www.ea.com/technology/news/inside-dead-space-4-the-intensity-director). **P:** check causal truth first, then combined experience; references do not supply Eyesore acceptance numbers. DUSK/Prodeus official descriptions support genre/editor/identity reference, not measured quality superiority or exact tell timing. [DUSK](https://store.steampowered.com/app/519860/DUSK/), [Prodeus](https://store.steampowered.com/app/964800/Prodeus/).

GDC's [in-house playtesting talk page](https://gdcvault.com/play/1016497/Implementing-an-In-House-Playtesting) establishes the talk's iterative/budget scope; the full lecture was not inspected. No detailed methodology is attributed to its abstract. Reference media still require a logged viewing/listening pass before precise scene/spectral/timing claims.

## Controls, counterbalance and practical sessions

**P shared profile:** exact engine/build/content/seed/RNG/tick values; feet/camera/body/target dimensions, aim/FOV and projection; action/HP/damage/cadence/loadout; roster/activation/placements; map/exit/resource state; material/actor/tell/FX treatment; audio sources/gains/duck/transport/loop settings; input bindings and comfort settings; display/device/capture identity. Tuning bands become exact profile values before trials. This does not freeze production balance.

Use 2–3 people for short formative fault-finding, including the user when available; expand only when alternatives are distinguishable and technically truthful. Include first-time genre users and experienced shooter players if feasible and report who actually played. Five players is still diagnostic, not population proof. The user is product decision-maker, and a lone preference matters to their goal; do not disguise it as universal preference.

For two alternatives, balance AB/BA where feasible; for three, rotate starting order across participants and note unbalanced allocation. Anonymous labels reduce theme/name/loudness expectations without hiding controls or access needs. One warm-up neutral action establishes input familiarity, not a tour of the candidate's solution. Keep safety/comfort changes available; log changes and analyze that profile separately. Breaks and stop-on-fatigue/discomfort are part of credible repetition. Long all-day agent throughput is not a demand for long human sessions.

First C navigation cannot be “reset” to naive by retry. Keep first-visit behavior separate, use independent unfamiliar players or equivalent undisclosed layouts when available, and label unmatched spatial differences. Learning is a real outcome in repeated routes but confounds first-use navigation. For fixed event clips, rotate a small agreed set of equal-opportunity attacks and log exposure; repeated screenshots are not independent participants. Ask uncued descriptions before naming roles; then a focused followup may identify where information was lost.

Audio perceived-level matching needs an actual listener at comfortable fixed playback settings. Record gains and onset/active-window/whole-clip measurements; don't force short transients or sparse music to equal integrated LUFS. Same source/processing/timing when investigating mixer; different source is a separate named variable. A null source comparison means neither source earned a preference, not automatic acceptance of previous rejected audio. Unknown monitoring hardware limits transfer to other listeners.

## Capture timing and performance evidence

**P adopt role16/19 clocks:** input observation, simulation tick/event, enqueue time, audio output frame/useful source-onset frame, postmix/live loopback stamp, rendered frame/video timestamp. Display/speaker physical delay is separately measured with uncertainty; simulation timestamp alone is not sound arrival. 15fps video has ~66.7ms frame spacing, inadequate to certify a10ms alignment difference. Offline event-render proves digital sequencing under pinned configuration, not hardware playback. Actual live monitor capture is not proof of physical speaker latency. Capture gaps, cue drops, clipping/decoder failure and uncontrolled profile mismatch invalidate the affected comparison; preserve partial record with reason.

Performance compares named hardware/OS/driver/device/build, viewport/render scale/vsync/target refresh, same actor/projectile/effect/light/audio stress and duration. Record frame-time series and spikes/95th/99th quantiles, CPU/GPU sections when measurable, audio callback deadline/slack/underflows, capture drops, memory/asset load time, and simultaneous live streams/overdraw. A60Hz goal gives16.67ms display-frame interval as arithmetic, not an approved supported-machine budget. Select actual supported hardware/target with role01/19, then define headroom and sustained/spike criteria. Shader/compiler warm-up, startup loads and steady play are separate windows; cold launch and warmed repeat both matter.

Capture-on/off and overlays-on/off are separate measurements: recording may stall the current frame loop; instrumentation can change results. A dt clamp that slows world time must not make a stressed scene “pass” by doing less simulation. Mean FPS can hide lethal stutters; whole-session averages can bury one masked warning. Do not infer GPU cost from texture byte arithmetic, audio latency from512 requested frames, or callback health from zero stolen-voice counts alone. Report insufficient samples/unsupported counters honestly.

## Severity, null results and metric hazards

**P fatal to the affected gate:** wrong artifact/profile; required missing actor/audio; dishonest success/cancel/amount; no feasible legal response to authored lethal attack; render/collision disagreement; softlock; stale generation action; input leakage; hidden map/caption reveal; incomplete audio capture used to approve sound. One reproducible structural failure remains a blocker even if most runs succeed.

**Repairable comprehension failure:** genuine cue exists but role/phase/route/lock/material repeatedly confused. Record the cause/window; repair shape, duration, background, mix, text or layout based on evidence. Repeat the same case before broad asset expansion. Player damage alone is not proof of unfairness; show opportunity and decision.

**Valid style/preference result:** both alternatives satisfy truth/readability, user prefers one, ties, or dislikes both. Keep their reasons without converting taste into bug or forcing selection. Conventional mechanics are not disqualified because no unprecedented verb was noticed. “Originality” cannot be proven by a recognition test; review concrete identities/derivation rights and user distinction separately.

Result labels are `passed technical gate`, `failed`, `pending`, `invalid comparison`, `no clear difference`, `mixed by context`, `preferred`, `rejected`, or `not evaluated`. Report every planned profile/case, including abandoned/invalid sessions and reasons. Do not present only favorable captures or count missing responses as preference. Both candidates failing returns to redesign; both collapsing to control merges the redundant option. User rejecting all audio is a source/design outcome even when engineering is clean.

90% role/tell recognition is a provisional flag across several reports, not a release certificate. With20 clips,18 correct sounds precise but may repeat one player's learned cue; show per-person/per-role/view/phase errors and actual denominators. Whole-target mask15%, crucial-feature5%,3×3 pixels,100ms delay and30s navigation stall thresholds are hypotheses to investigate. Pixel fractions unstable for tiny features, hand-marked masks/timing uncertain, and whole-session means conceal worst legal view. Replace ambiguous “more than one displayed frame” with logged duration as well: one frame at15fps differs from one at144Hz.

TTK depends on accuracy/path/learning, not only weapon DPS; damage taken can fall because a player retreats or avoids optional combat. Route time includes fights/inspection/preferences; fast completion is not automatically good navigation. Low ammo remainder is not automatically interesting economy. Interrupt count can reward stun-lock; high kill rate can imply trivial enemies. Loudness scores can favor painful attack peaks. Recognition tests can coach vocabulary; repeated novel mechanic trials can manufacture familiarity. Use metrics to explain events, never a single weighted quality score or significance claim from tiny convenience samples.
